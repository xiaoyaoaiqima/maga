# MAGA 训练成熟度与 RAAP 资产发布方案

> 状态：架构草案  
> 数据快照：2026-07-21  
> 适用范围：旺玥、莼悦、A2 舆情改善评论、A2 礼遇、源悦等内容生成业务

## 1. 核心结论

MAGA 应当负责业务规则、语料和 Prompt 的实验、训练、评测与发布，是内容生成资产的 source of truth。

RAAP 不应继续现场填写或修改 MAGA 管理的业务语料。RAAP 的职责应收敛为：

- 消费 MAGA 已验收、已发布的资产版本。
- 保存可独立运行的只读资产快照。
- 选择版本、升级、回滚和暂停使用。
- 将运行问题和运营反馈回流 MAGA。

这里的“训练”主要指规则、语料、Prompt、审核器和生成链路的持续迭代，不等同于模型微调。

RAAP 应当在资产逻辑上依附 MAGA，但不应在每次生成时实时请求 MAGA。推荐由 MAGA 发布不可变版本包，RAAP 导入并缓存该版本，避免 MAGA 故障影响 RAAP 的在线运行。

## 2. 系统职责边界

### 2.1 MAGA 负责

- 维护候选业务规则和语料。
- 使用真实生成链路执行实验批次。
- 执行机器评测、合规检查、多样性检查和人工业务评审。
- 记录生成失败、改写、人工反馈及资产迭代过程。
- 计算资产版本的训练成熟度。
- 审批并发布可供 RAAP 消费的版本包。
- 接收 RAAP 回流的问题，形成下一版候选资产。

### 2.2 RAAP 负责

- 保存 MAGA 发布包的只读快照。
- 将 Expert 绑定到明确的 MAGA 发布版本。
- 使用发布版本执行生产任务。
- 展示来源、版本、成熟度、发布时间和审批信息。
- 支持版本升级、回滚、暂停使用。
- 将生产反馈提交回 MAGA。

### 2.3 RAAP 不再负责

- 直接新增或编辑 MAGA 管理的业务规则、业务关键词和业务语料。
- 在 RAAP 内独立修改已经发布的资产快照。
- 将未经 MAGA 评测的临时语料直接投入生产。
- 通过复制原始语料的方式制造多个不可追踪版本。

asset_key

+ asset/content hash
+ model route/config hash
+ prompt/evaluation profile

### 3.1 当前指标暴露的问题

#### hard pass 不能等于训练成熟度

A2 礼遇 v11 的机器 hard pass 为 100%，但人工直接可用率只有 30%。这说明当前机器审核还没有覆盖实际业务口径，不能仅凭 hard pass 发布资产。

#### 改写率必须区分机器后处理和人工审核

A2 礼遇 v11 的首轮生成中，10 篇全部生成成功，6 篇经过生成后链路处理：4 篇涉及确定性词面规范化，3 篇调用模型做语义改写，其中 1 篇同时经过两类处理。机器后链路结束后没有遗留待处理项。

但人工首审只有 3 篇直接可用，另外 7 篇因为标题、奖品归属、检测承接、报名描述或虚构兑换经历被要求修改。修改后 7 个候选均被采纳，最终 10 篇可用。

这几类“改写”含义不同：

- 确定性词面规范化是主动下沉到后链路的架构选择，例如将固定词面替换从生文 Prompt 移出，不应直接降低资产成熟度。
- 机器语义改写反映额外模型成本、延迟和事实漂移风险，需要单独观察。
- 机器后链路结束后仍需处理，才代表自动链路没有完成质量收敛。
- 人工要求修改率反映首轮内容离直接业务使用还有多远，是资产成熟度的核心指标。
- 修改后最终可用率只说明人机协同能够完成交付，不能证明资产已经达到直接发布标准。

当前批次报告的 `rewrite_item_count` 还会把生成后处理和人工反馈改写混合计算。同一个 A2 礼遇 batch 731 在人工反馈前为 6，提交人工改写后变成 8，因此该字段不能直接用于 readiness 聚合。

#### 莼悦存在指标口径错误

莼悦 v26 的生成结果中：

- 业务可用性审核器判定为 `direct_pool`。
- AI 味审核通过。
- 没有要求改写。
- 但由于运行使用 `postprocess_mode=generate_only` 且 `audit_skipped=true`，顶层 `hard_pass` 仍为 false。

因此，莼悦当前显示的 0 hard pass 不是内容全部失败，而是质量状态聚合逻辑不一致。该问题必须先修复，否则成熟度会被错误计算。

#### 资产版本切换会使旧评测失效

- 旺玥 v76 的通过结果不能算作 v80 的评测结果。
- 莼悦 v26 的结果不能证明 v27 可发布。
- A2 礼遇 v10 的人工反馈只能作为 v11 的历史对照，不能直接计入 v11 连续达标批次。

## 4. 训练成熟度指标

MAGA 建议同时展示：

- `Training Readiness Score`：0～100 分，用于观察持续改善趋势。
- `Maturity Level`：L0～L4，用于表达当前所处阶段。
- `Publish Gate`：可发布/不可发布，用硬门槛做最终决策。
- `Blockers`：明确列出未通过的条件，避免只显示一个无法解释的分数。

### 4.1 成熟度等级

| 等级 | 名称 | 定义 |
| --- | --- | --- |
| L0 | 未建规则 | 业务资产尚未形成，不能运行 |
| L1 | 可以运行 | 已能完成真实链路生成，但质量尚未稳定 |
| L2 | 机器质量稳定 | 生成、合规和机器质量指标基本稳定 |
| L3 | 人工业务可用 | 经过人工评审及必要修改后，可以形成业务交付 |
| L4 | 可发布 RAAP | 同一版本连续稳定，达到直接业务使用标准，已完成审批和版本固化 |

### 4.2 建议评分维度

| 维度 | 权重 | 核心指标 |
| --- | ---: | --- |
| 运行稳定性 | 15 | 原始生成成功率、资产导致的生成失败率、供应商或系统失败率、异常重试率 |
| 机器质量 | 20 | hard pass、合规、事实与规则审核、机器后链路未解决率 |
| 人工直接可用性 | 25 | direct usable/approve 比例，而不是修改后的最终通过比例 |
| 修改成本 | 15 | 模型语义改写率、人工要求修改率、人工编辑量、改写轮次；确定性规范化率只观察 |
| 多样性 | 10 | Jaccard、重复表达、结构与内容路径分布 |
| 规则覆盖 | 10 | 业务规则、场景和主要组合的测试覆盖率 |
| 可复现性 | 5 | 资产 hash、模型配置 hash、评测版本和运行快照是否完整 |

评分只用于排序和观察趋势，不得绕过发布硬门槛。例如机器质量很高，不能抵消人工直接可用率不足。人工要求修改率与人工直接可用率互为反向口径时不得重复计分。

### 4.3 改写与可用性指标口径

成熟度计算至少需要拆出以下指标，不能继续只使用一个 `rewrite_item_count`：

| 指标 | 建议计算方式 | 用途 |
| --- | --- | --- |
| 原始生成成功率 | 产出完整标题和正文的条数 / 发起生成条数 | 判断真实生成链路是否稳定 |
| 确定性规范化率 | 经过固定替换或删除的内容条数 / 已生成条数 | 观察后链路工作量，不直接扣成熟度 |
| 机器语义改写率 | 调用模型完成生成后语义改写的内容条数 / 已生成条数 | 评估成本、延迟和事实漂移风险 |
| 机器后链路未解决率 | 自动处理结束后仍标记待处理的条数 / 已生成条数 | 机器质量硬门槛 |
| 人工直接可用率 | 首次人工审核直接 approve 的条数 / 已人工审核条数 | 资产直接业务可用性的核心指标 |
| 人工要求修改率 | 首次人工审核 `request_revision` 的内容条数 / 已人工审核条数 | 衡量资产首轮修改成本 |
| 人工编辑率 | 发生 `manual_edit` 的内容条数 / 已人工审核条数 | 衡量纯人工操作成本 |
| 改写候选接受率 | `accept_rewrite` 数量 / 已产生系统改写候选数量 | 衡量审核改写 Expert，不代表首轮资产成熟度 |
| 修改后最终可用率 | 修改后最终 approved 或 usable 的条数 / 已生成条数 | 衡量人机协同交付能力 |

生成成功率还应拆分失败原因。由资产、Prompt 或输出格式导致的失败计入资产成熟度；供应商超时、网络中断等运行环境问题单独计入平台稳定性，不能与内容资产质量混为一谈。

建议批次报告持久化以下互不覆盖的字段：

```text
raw_generated_count
asset_generation_failed_count
platform_generation_failed_count
deterministic_normalized_item_count
machine_semantic_rewrite_item_count
machine_unresolved_item_count
human_direct_approved_count
human_revision_requested_count
human_manual_edited_count
operator_rewrite_accepted_count
final_usable_count
```

这些首轮生成和机器后处理指标应保存为不可变评测快照。后续人工反馈可以新增人工审核指标，但不能反向改变首轮机器改写率。

### 4.4 L4 发布硬门槛

初版建议：

- 同一资产版本、同一模型配置和同一评测口径连续至少 3 批达标。
- 文章累计样本不少于 30 篇；评论累计样本不少于 150 条。
- 资产侧原始生成成功率不低于 98%，并同时展示成功条数、发起条数和失败原因；文章只有 30 篇时，该门槛实际等同于 30/30 成功。
- 资产导致的生成失败和平台或供应商失败必须分开统计；平台或供应商成功率进入独立运行 SLO 和平台发布门槛，不计入内容资产质量分。
- 机器 hard pass 不低于 90%，且 hard pass 聚合口径已经校验。
- 机器后链路结束后仍需人工处理率不高于 5%。
- 人工直接 usable/approve 比例不低于 80%。
- 确定性规范化率不设置统一发布上限；模型语义改写率作为成本和稳定性指标展示，后续按业务校准阈值。
- 文章最大 Jaccard 不高于 0.35。
- 评论最大 Jaccard 不高于 0.45。
- 发布范围内的业务规则分支覆盖率为 100%。
- 首轮机器结果和首次人工评审中均无 P0 合规、事实或活动机制错误；P0 问题不能通过修改后通过来抵消。
- 最新资产版本已经完整复测，不能继承旧版本结论。
- 资产、Prompt、模型配置和评测规则具备可复现 hash。
- 已记录审批人、审批时间及可回滚版本。

不同业务后续可以校准阈值，但不得删除“人工直接可用率、版本一致性、覆盖率和 P0 问题”这些硬门槛。

## 5. MAGA 到 RAAP 的发布流程

```text
MAGA 候选资产
  -> 基准批次
  -> 机器评测
  -> 人工业务评审
  -> 连续稳定性验证
  -> 达到 L4
  -> 人工审批
  -> 生成不可变发布包
  -> RAAP 导入只读快照
  -> 生产运行
  -> 反馈回流 MAGA
```

### 5.1 MAGA 发布包

发布包至少需要包含：

```text
release_id
business/expert identity
asset_key
asset_type
version_no
asset content snapshot
asset/content hash
system/common corpus references or snapshots
business-specific corpus references or snapshots
prompt/expert config snapshot
model route/config hash
evaluation profile/version
readiness score
maturity level
publish gate result
evaluation batch ids
evaluation report
approved_by
approved_at
previous_release_id
created_at
```

RAAP 导入后应验证发布包 hash，不能根据 label 或 name 临时重新拼装一套业务资产。label/name 去重仍可用于迁移时识别人类语义相同的节点，但生产运行必须绑定已经固化的发布版本。

### 5.2 RAAP 运行方式

RAAP 不需要在每次生文时调用 MAGA，而是：

1. 从 MAGA 导入已发布版本。
2. 验证 manifest 和内容 hash。
3. 保存本地只读快照。
4. 将 Expert 绑定到 `release_id`。
5. 使用本地快照运行。
6. 将错误、修改和运营反馈回传 MAGA。

### 5.3 RAAP 页面应展示

- `来源：MAGA`
- MAGA 业务线/Expert
- 当前 `release_id`
- 资产版本和内容 hash
- 成熟度分数及等级
- 发布审批人和时间
- 当前版本是否落后于 MAGA 最新发布版本
- 升级、回滚、暂停使用操作
- 问题反馈入口

对 MAGA 管理的 Expert，语料和业务规则区域只读，不再提供直接新增、编辑和删除入口。

## 6. RAAP 现有语料迁移与清理

现有 RAAP 业务语料不应立即无差别删除，应按引用关系完成一次切换：

1. 识别每个 RAAP Expert 当前实际引用的规则和语料。
2. 在 MAGA 中找到或建立对应业务资产。
3. 在 MAGA 中完成真实生成、评测和人工验收。
4. 发布 MAGA 版本包。
5. 将 RAAP Expert 切换到新的 `release_id`。
6. 验证生产生成和下游文章读取链路。
7. 删除已经解除引用的 RAAP 历史业务语料。

不建议继续增加“归档语料/归档节点”状态。切换前保持现状，切换并确认无引用后直接删除；如果仍被策略引用，则先恢复或迁移引用，不能用归档状态隐藏引用问题。

Expert 跨系统迁移时，应优先迁移 MAGA 发布包或发布引用，而不是在目标 RAAP 中重新手工创建一份原始关键词语料。

## 7. 实施顺序

### 第一阶段：修正指标可信度

- 修复莼悦 `direct_pool` 与顶层 `hard_pass=false` 的状态不一致。
- 拆分原始生成成功率、确定性规范化率、机器语义改写率和机器后链路未解决率。
- 区分人工直接可用率、人工要求修改率、人工编辑率、改写候选接受率和修改后最终可用率。
- 将首轮机器指标固化为不可变快照，避免人工反馈反向改变 `rewrite_item_count`。
- 区分资产导致的生成失败与供应商或平台运行失败。
- 确保批次报告记录准确的资产版本、模型配置和评测版本。

### 第二阶段：增加 MAGA 成熟度能力

- 增加按 `asset_key + version_no` 聚合的 readiness API。
- 增加成熟度分数、等级、发布门槛和 blocker 展示。
- 增加规则分支覆盖率和连续批次稳定性统计。
- 最新资产发生变化后，自动将旧成熟度标记为过期，要求重新评测。

### 第三阶段：增加发布包

- 在 MAGA 增加 release candidate 和 publish 操作。
- 固化资产、Prompt、模型和评测快照。
- 生成 manifest、hash、审批记录和回滚关系。

### 第四阶段：RAAP 只读消费

- RAAP 增加 MAGA 发布包导入和校验。
- Expert 绑定 `release_id`。
- MAGA 管理的语料和规则改为只读。
- 增加升级、回滚、暂停和反馈回流。

### 第五阶段：清理历史 RAAP 语料

- 按 Expert 和策略引用关系逐个切换。
- 验证生成及下游读取。
- 删除不再引用的旧业务语料和重复节点。

## 8. 当前最优先事项

1. 修复莼悦质量状态聚合错误，否则成熟度指标不可用。
2. 对旺玥 v80 补齐第三批基准测试和人工评审，并补充可复现 hash。
3. 对 A2 舆情评论降低同质化并提升人工直接 usable 比例。
4. 对 A2 礼遇继续提高首次直接可用率，不能把人工改完后的 100% 当作模型成熟。
5. 对源悦最新资产重新执行基准批次。
6. 完成 readiness 指标后，再开放 MAGA 到 RAAP 的正式发布能力。

## 9. 与文章读取兼容方案的关系

本文定义的是“规则、语料和 Expert 资产如何从 MAGA 发布到 RAAP”。

最终文章如何写入兼容表、如何被老 RAAP `/match` 和 `/use` 读取，仍按 [MAGA_COMPAT_OLD_RAAP_CONTENT_MATCH.md](./MAGA_COMPAT_OLD_RAAP_CONTENT_MATCH.md) 的过渡期方案处理。

两者的边界是：

- 本文负责生成前的资产所有权、训练成熟度和版本发布。
- 兼容文档负责生成后的文章存储、匹配、锁定和消费。
