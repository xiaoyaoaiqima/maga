# MAGA MVP 架构

本文档用于明确 MAGA 在 MVP 阶段的产品定位、用户交互和内部生文架构。

当前阶段的核心目标不是做一个“复杂的策略配置平台”，而是做一个对目标用户足够简单、对结果足够稳定的内容生产产品。

一句话定义：

- 帮品牌、内容工作室和高频博主稳定产出可直接发布的小红书内容

---

## 一、MVP 产品定位

### 1. 产品定位

MVP 的产品定位锁定为：

- 帮品牌和博主稳定产出可发布的小红书内容

这意味着产品的核心价值不是“生成得多聪明”，而是：

- 稳定
- 可控
- 可直接发布

### 2. 目标人群

MVP 只服务以下三类核心用户：

- 小红书商家（带货商家、品牌方）
- 内容工作室
- 中腰部博主（有高频发文需求的人）

这三类用户的共同特征是：

- 有明确发文任务
- 对效率敏感
- 对内容稳定性敏感
- 不希望学习复杂的策略配置逻辑

### 3. MVP 核心卖点

MVP 只强调一个结果：

- 给很少的输入，产出一篇结构清晰、风格明确、可以直接复制发布的小红书内容

不强调：

- Agent 多复杂
- 策略推理多完整
- 后台配置多灵活

这些能力都属于系统内部，不属于用户心智。

---

## 二、MVP 产品原则

### 1. 前台必须简单

前台页面必须是任务页，不是配置页。

用户应该感受到的是：

- 我输入要写什么
- 我选一个风格
- 我点生成
- 我拿到一篇能发的内容

而不应该感受到：

- 我要先理解策略字段
- 我要组合多个维度
- 我要配置 Expert
- 我要管理 Agent 编排

### 2. 复杂度全部下沉到后台

以下概念在 MVP 中都属于系统内部概念，不对用户暴露：

- Agent
- Multi-Agent 编排
- Expert
- 策略组合
- strategy variant
- Prompt 模板拼装
- 插件渲染链路

这些概念可以继续存在，也可以继续演进，但只能作为内部实现手段。

### 3. 语料系统是可选增强，不是使用门槛

用户可以管理语料系统，但不应该被要求先配置语料才能生成内容。

因此，MVP 对语料系统的定位是：

- 可选增强能力
- 后台可维护能力
- 用于提升稳定性和可控性的底层资源

而不是：

- 每次任务都必须编辑的表单项
- 普通用户必须理解的主交互对象

---

## 三、MVP 用户侧功能范围

MVP 前台保留两个用户能理解的概念：

- 实际产文：围绕产品/主题、目标人群、风格，一键生成可发布内容。
- 训练反馈：对已生成内容做通过、要求修改或人工改写，反馈会沉淀到后续资产、规则和 Prompt 优化。

这两个概念面向用户，但底层 Agent、Expert、Prompt、执行 trace 仍然隐藏在后台。

### 1. 实际产文输入

用户在任务页只填写 3 个字段：

- `产品/主题`
- `目标人群`（选填）
- `风格`

说明：

- `产品/主题` 是本次内容的核心输入，必须填写
- `目标人群` 允许为空，不填时系统使用默认理解
- `风格` 是用户唯一需要明确选择的内容控制项

枚举具体项（风格、人设、产品词表、语料）暂不在文档中展开，详见 §七.4。

### 2. 实际产文生成

用户只看到一个动作：

- `一键生成`

生成过程中，用户不需要参与中间决策，也不需要选择策略组合。

### 3. 实际产文输出

输出必须是一个可直接使用的结果，而不是中间材料。

MVP 的标准输出为：

- 标题
- 正文

输出结果要求：

- 结构清晰
- 风格明确
- 语言自然
- 具备小红书内容感
- 可直接复制发布

不输出：

- 策略解释
- 字段拆解
- 关键词组合说明
- Agent 运行日志
- JSON 结果

### 4. 训练反馈

生成后用户可以对内容做轻量反馈：

- 通过：内容可以进入待发布或样稿池。
- 要求修改：记录不满意原因，进入后续优化队列。
- 人工改写：保存人工改后的标题/正文，作为训练反馈样本。

反馈不是新的生文必填步骤，不阻塞用户继续生成。MAGA 后台会把反馈保存为 `content_feedback` 和版本记录，后续由 `maga-worker` 的 `feedback.*` / `prompt.*` 能力用于总结问题、提出资产或 Prompt 更新建议。

## 四、MVP 前台交互形态

### 1. 实际产文主链路

前台主链路固定为：

```text
输入产品/主题
  ↓
选择目标人群（可选）
  ↓
选择风格
  ↓
一键生成
  ↓
获得标题 + 正文
```

这条链路是 MVP 的产品核心，不再增加额外主步骤。

### 2. 训练反馈链路

反馈链路固定为：

```text
查看生成结果
  ↓
通过 / 要求修改 / 人工改写
  ↓
记录反馈与版本
  ↓
后台聚合为训练和优化素材
```

反馈入口应贴近结果卡片或批量报告，不要求用户理解 Agent trace。

### 3. 页面形态

MVP 首页应是一个极简任务页，而不是多模块后台；但可以有两个清晰 tab：

- `实际产文`：默认页，承载单篇生成和批量生成。
- `训练反馈`：展示已生成内容的人工反馈、改写版本和待优化样本。

推荐结构：

- 顶部：一句话价值说明
- 中间：任务输入区
- 底部：结果展示区

任务输入区只保留：

- 产品/主题输入框
- 目标人群输入框或轻量选择器
- 风格下拉框
- 生成按钮

结果展示区只保留：

- 标题
- 正文
- 复制操作

说明：MVP 输出口径固定为“标题 + 正文”。hashtag/话题标签暂不作为交付字段；如生成链路内部保留 tags，只用于内部实验，不展示、不写入 start_generation 响应。

### 4. 前台不做的事

MVP 前台明确不做以下内容：

- 不展示策略字段面板
- 不展示 Agent 编排图
- 不展示关键词组合器
- 不强迫用户维护语料
- 不让用户理解插件体系
- 不让用户理解 Prompt

---

## 五、内部生文架构

虽然前台必须极简，但后台仍然需要一套完整的内容生产链路，以保证结果稳定、可控、可发布。

### 1. 内部主流程

MVP 推荐的内部工作流如下：

```text
用户输入任务
  ↓
任务意图规范化
  ↓
策略补全
  ↓
内容生成
  ↓
风格优化
  ↓
可发布性检查
  ├─ 通过 → 输出最终内容
  └─ 不通过 → 定向改写 → 再检查
```

对用户隐藏后，前台仍然表现为：

```text
输入 → 生成 → 输出
```

实现层 capability 映射详见 [EXECUTOR_PROTOCOL.md](./EXECUTOR_PROTOCOL.md) §五。

### 2. 各内部层职责

#### 任务意图规范化层

职责：

- 解析用户输入的产品/主题
- 补全必要的上下文
- 将“目标人群为空”的情况转成系统可用输入
- 生成统一的内部任务结构

这一层的目标不是写内容，而是把简单输入转成可计算的任务上下文。

#### 策略补全层

职责：

- 在用户不感知的情况下确定内容打法
- 根据输入和风格选择合适的表达路径
- 选择或补全内部策略参数

重要原则：

- 策略层保留，但不暴露给用户
- 用户不再直接配置策略字段
- 策略是内部控制结构，不是产品主交互

#### 内容生成层

职责：

- 生成首版标题和正文
- 将任务信息、风格信息和底层语料整合成一篇完整内容

这一层产出的重点是“能成文”，但不要求已经是最终可发版本。

#### 风格优化层

职责：

- 让内容更像小红书
- 让语言更自然
- 让风格和用户选择保持一致
- 降低机器感和模板感

#### 可发布性检查层

职责：

- 检查标题和正文是否符合输出要求
- hard AE 任一不过时，触发一次定向改写；改写输入必须带上一轮 draft 与完整 review_report
- 最终返回给前台的结果只包含 title/body，不包含 hashtags
- 检查结构是否完整
- 检查是否有明显违禁或过强广告感
- 检查是否达到“可以直接复制发布”的标准

如果不通过，则进入定向改写，再次检查。

### 3. Agent 执行层定位

MVP 阶段允许将模型执行外置到 Hermes profile 或其他 runtime 中，但 MAGA 仍然是营销内容生成的业务工作台和 source of truth。默认 Hermes profile 统一命名为 `maga-worker`，当前只暴露 `asset.import`、`content.generate`、`content.rewrite`。

职责边界：

- MAGA 负责业务规则、系统关键词、Expert 配置、模型参数、任务、trace、artifact、违禁词审核和人工反馈。
- Hermes `maga-worker` 负责具体执行：按 MAGA 下发的 prompt 调用模型，返回生成或改写结果。
- Hermes 不直接读写 MAGA 数据库，只通过 MAGA API 交互。
- MAGA 不改造成通用 Agent 平台，只保留轻量 executor 抽象，以便未来替换执行层。

当前执行协议见：[MAGA Worker Executor Protocol](./EXECUTOR_PROTOCOL.md)。完整生文协作流程见：[AI 生文流水线协作流程](./AI_CONTENT_GENERATION_WORKFLOW.md)。

## 六、配置分层

为了同时满足“前台简单”和“结果可控”，MVP 的配置必须分层，而不是把所有能力都压到任务表单里。

### 1. 运营输入层

运营主流程只要求上传业务规则包。规则包由运营提前拆解一次生文需求中的方向、语料、示例和补充说明，生成时不再要求手填主题、人群、风格。

单篇临时调试可以保留临时主题输入，但不作为正式运营主链路。

### 2. 系统配置层

这部分用于提升稳定性和一致性，由内部运营或系统管理员维护。

当前配置包括：

- 系统提示词关键词：可扩展类别，每个启用类别自动选择一个子关键词。
- 生文 Expert：提示词模板 + provider、model code、temperature、max token 等模型参数。
- 模型配置：Provider、可用模型和默认模型。
- 业务违禁词：审核流程使用，不塞进首轮生文 prompt。

这些配置的作用是降低重复输入，提高内容一致性，并让生成、审核、改写可追踪。

### 3. 执行控制层

MAGA 负责任务、trace、违禁词审核、相似度审核、改写触发和反馈记录。`maga-worker` 只执行 MAGA 下发的 `asset.import`、`content.generate`、`content.rewrite`。

旧 `xhs.*`、`comment.generate`、自动学习类能力不再作为当前运行能力。

## 七、系统关键词定位

### 1. 作为系统提示词配置保留

系统关键词在 MVP 中继续保留，但不再是旧的固定 keyword corpus 系统。它是可扩展的提示词语料资产：

- 支持新增类别，不把类别枚举写死为四类。
- 每个启用类别默认自动选择一个子关键词。
- 每个子关键词可维护多条语料。
- 生成链路把选中的语料聚合成 `keyword_corpus` 注入 Expert 模板。

当前默认类别是人设、生文指令、生评论指令、扰动规则、写作手法、格式控制，但它们不是系统上限。

### 2. 用户与系统关键词的关系

运营生成内容时不需要逐个选择关键词。系统会根据启用类别自动选择，并把选择结果写入批次计划和 trace。

内部可以进入系统关键词管理页维护类别、子关键词和语料。新增类别后，生成链路不需要改 worker capability 或 Expert 模板，只要模板继续使用聚合变量。

### 3. 系统关键词对生成链路的作用

语料系统在内部主要承担以下职责：

- 提供表达视角和语气控制。
- 提供生文或生评论的任务指令。
- 提供扰动、多样性和写作手法。
- 提供格式控制，例如字数、emoji、段落排版。

业务规则包决定“这次写什么”，系统关键词决定“怎么写”。

## 八、可发布内容的定义

MVP 既然承诺“可直接发布”，就必须定义什么叫“可发布内容”。

### 1. 最低标准

一篇可发布内容至少满足：

- 有标题
- 有正文
- 正文结构完整
- 语言自然
- 风格一致
- 没有明显机器感
- 没有明显违规或过强广告感

### 2. 结果形态标准

最终输出应是：

- 一篇完整文案

而不是：

- 提纲
- 半成品
- 多段素材拼接
- 策略说明

### 3. 内部质量目标

系统内部应尽量保证：

- 首屏就能给出可用结果
- 用户只需轻微修改甚至不用修改
- 不需要先做复杂配置才能得到结果

## 九、MVP 边界

### 1. 本期明确要做的

- 极简任务页
- 3 个输入字段
- 一键生成
- 标题 + 正文输出
- 内部自动策略补全
- 风格优化
- 可发布性检查
- 语料系统作为可选增强能力保留

### 2. 本期明确不做的

- 不做策略配置型前台
- 不做用户可见的多 Agent 工作台
- 不做用户可见的关键词组合器
- 不做重型插件编排产品
- 不做要求用户先维护语料才能使用的流程
- 不做面向所有写作场景的通用写作助手

### 3. 产品边界一句话总结

MVP 只解决一件事：

- 让目标用户用最少输入，稳定拿到一篇可直接发布的小红书内容

---

## 十、后续演进方向

MVP 跑通后再决定演进，优先级三条原则：先优化结果质量（可发布率、风格稳定性、品牌一致性、直接使用率）再扩前台字段；以用户实际修改行为决定是否开放控制项；任何复杂控制项做成高级模式或后台能力，不重做前台。

---

## 十一、结论

MAGA 在 MVP 阶段的正确产品形态，不是“把关键词策略系统直接搬到前台”，而是：

- 前台极简
- 后台复杂
- 语料可选
- 编排隐藏
- 输出直接可用

最终产品应让用户感知到的是：

- 我只需要告诉系统我要写什么、给谁看、想要什么风格
- 系统就能给我一篇能发的小红书内容

这就是本阶段最重要的产品逻辑。
