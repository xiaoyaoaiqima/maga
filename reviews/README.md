# 运营审核反馈账本

这里记录会反复审核、反复迭代的内容链路口径。原则是按长期业务链路沉淀，不按每一次临时需求新开文件。

## 当前账本

- `yuanyue_product_content_review_rules.md`：源悦生文，记录产品使用体验、月龄/周期、功效表达、真人感和运营打回点。
- `yuanyue_comment_review_rules.md`：源悦评论，记录业务规则、短评口吻、产品向评论、购买/活动/渠道表达和同质化问题。
- `a2_plot_discussion_review_rules.md`：A2 剧情讨论评论，记录剧情事实、孩子视角、对讲机活动边界和专属剧情口径。

## 迭代方式

1. 新产物审核：先找到所属链路，读取对应账本和相关 skill，再输出审核结论。
2. 运营反馈吸收：先追加到账本的 `迭代记录`，标清日期、反馈原话或问题类型、最终口径。
3. 稳定审核规则：同步到 `skills/` 下对应审核 skill，保证下次自动使用。
4. 影响生成的规则：再同步到 `关键词语料/` 或 `prompts/`，避免只会审核、不会改生成。
5. Prompt 分层检查：吸收运营反馈或看新产物时，注意不要把重业务规则塞进 `人设`、`生文指令/生评论指令`、`扰动规则`、`格式控制/评论格式控制`。这些通用系统关键词只负责语气、生成动作、随机性和输出形态；重业务规则放业务规则包/业务规则，可复用边界放表达写作规则，强制底线放硬性规则。
6. 本地跑批交付：用户要求“跑一批/跑完看看”时，默认导出 `.xlsx` 结果文件；聊天里只做摘要，不用纯文本列表代替文件。导出明细只保留非空结果，空输出只在摘要里统计，不写入 Results 明细表。评论结果表使用 `标题`、`正文`、`上下文变量(context_list)` 结构，其中 `标题` 默认为空，`正文` 放评论正文，`上下文变量(context_list)` 用 JSON 字符串记录本条使用的人设、扰动规则、生文指令、业务规则、生文输出格式等关键词上下文。

## 新建账本边界

只有出现新的长期业务链路时才新建账本，例如新品活动生文、妈妈班活动评论。单次批量审核、单个运营问题、单个误判校准，都追加到已有链路账本。
